# Project pack, autonomy, and handoff

## Generated layout

The scaffolder creates dedicated, conflict-safe files:

```text
.architecture/
  policy.yaml
  baseline.json
  exceptions.yaml
  decisions.json
  verification.json
  evidence.md
  agent-instructions.md
scripts/architecture/
  verify.py
  validate_policy.py
  watch_guardrail.py
  validators/
  fixtures/
agent-state/architecture-guardrail/
  loop-state.md
  decisions.md
  failed-attempts.md
  verification-ledger.md
  watch-cursor.json
.claude/agents/                 # when selected
.codex/agents/                  # when selected
.githooks/pre-commit
.github/workflows/architecture-guardrail.yml
docs/prompts/guardrail-forge-driver.md
```

The script previews by default and writes only with `--apply`. Git itself must
identify the target as the exact worktree root; a `.git` marker alone is not
authority, and inherited `GIT_*` variables cannot redirect this check. The
script captures the root identity before asking Git, carries that same identity
through preflight and every protected write, and rejects any swap even when all
destinations would be skipped. Windows holds a root handle without delete
sharing for the whole operation; POSIX holds the root descriptor, audits ctime
around Git/preflight, and creates through verified directory descriptors. It
preflights all destinations,
rejects symlink/path
escapes, and refuses the entire apply if any existing file differs. Files are
created exclusively and never overwritten. Because portable filesystems provide
no race-free conditional unlink, a late write failure never triggers destructive
rollback. Earlier paths and the possibly partial current destination are recorded
without claiming their bytes remain exact. Before the first destination write,
the scaffolder exclusively creates and flushes an `apply-in-progress`
`.guardrail-forge-recovery.json` record naming every planned destination. Only
after every destination succeeds does it exclusively create a matching
`.guardrail-forge-recovery.complete.json` record. A missing, malformed, linked,
or mismatched pair blocks every rerun until a human reviews the paths and repairs
the partial state. Duplicate JSON keys are invalid. Planned paths must be
non-empty, unique, exact safe relative
paths bound to the hashes of the generated bytes. Intent filesystem identity and
bytes are revalidated after every destination and on failure; an absent intent
is exclusively restored before control returns, while a replacement is never
overwritten. This includes failure while persisting the completion record. A
per-destination containment failure is handled by the same recovery path. A
detected identity/byte replacement also creates a separate exclusive
`.guardrail-forge-recovery.failed.json` record, so a same-byte replacement cannot
be laundered into success on the next run. A valid completed pair permits
identical reruns; it must be
human-archived before a later pack version can introduce new files. It never
edits existing `AGENTS.md`, `CLAUDE.md`, host settings, hooks, or workflows.
Merge the generated `agent-instructions.md` into existing instruction files only
after review.

The bundled git hook is not active merely because it exists. Prefer an existing
hook manager when present. Otherwise a human may opt into `core.hooksPath` after
reviewing how that affects every worktree. CI remains the authoritative gate.

## Autonomy ladder

| Level | Permission | Exit evidence |
|---|---|---|
| 1 | Read-only discovery and candidate/decision report. | Evidence map complete; conflicts and coverage gaps explicit. |
| 2 | Human approves exact rules; maker installs in an isolated worktree; breaker and verifier gate it. | Canary, fixtures, canonical verifier, existing repo gates, and independent verdict pass. |
| 3 | Forge may add or strengthen rules only when an existing approved decision clearly covers the exact scope. | Repeated Level 2 agreement and no new architecture judgment. |
| 4 | Forge may open guardrail PRs. Humans still review and merge. | Sustained Level 3 reliability plus approved connector/repository settings. |

Never infer promotion. Record the human decision and evidence that earned it.

## Hooks and CI

All local and hosted entry points execute:

```text
python scripts/architecture/verify.py
```

If a repo already has CI or hook configuration, integrate a call into its
existing structure rather than installing a duplicate workflow. Do not overwrite
or silently merge configuration. A checker must compare the wrapper command and
environment to the canonical invocation.

The generated GitHub workflow is a portable starting point, not proof that a
required status check or path-review rule is enabled. Hosted branch protection,
required reviewers, and workflow permissions require separate live evidence and
human authorization.

## Handoff to arch-drift-watch

On successful installation, configure `arch-drift-watch` to consume:

- Approved policy rules and their stable IDs.
- Exact baseline fingerprints and source commit.
- Approved exceptions and expiry/removal conditions.
- The canonical verifier's machine-readable findings where available.
- The authority digest and operational watch cursor. The cursor classifies
  new/persisting/resolved findings; it is not a second policy baseline.

First run the adapter normally. An uninitialized cursor blocks but returns the
exact authority digest. The architecture owner records that digest in
`.architecture/decisions.json` as one approved `watch-handoff` decision with
`subject_id: guardrail-pack`, and commits it with the reviewed pack. The adapter
reads that decision from `HEAD` and requires the working copy to match;
fabricated or merely uncommitted CLI strings are not authority. Every file
required to reproduce pack authority must also be tracked and unchanged from
`HEAD` by direct Git blob comparison, regardless of `assume-unchanged` or similar
index hints; committing only the decision is invalid. Then
initialize the committed cursor explicitly after a clean complete scan:

```text
python scripts/architecture/watch_guardrail.py --initialize --decision-id <approved-handoff> --approved-by <owner-id>
```

Normal runs use `python scripts/architecture/watch_guardrail.py`. They invoke
the canonical repo-only JSON verifier, retry one unstable repository snapshot,
block on malformed/incomplete/empty/changed authority, and atomically update only
the non-symlink, non-junction
`agent-state/architecture-guardrail/watch-cursor.json` after a complete scan. It
re-scans after the write and restores the prior cursor if verification changes.
The restoration is byte-for-byte, including original formatting.
Every active finding remains in output and
keeps exit `1`; the cursor only adds `new` or `persisting` labels, so editing it
cannot make drift green. An approved policy-pack change uses
`--accept-authority-change` with a new decision and owner after a clean scan.

The watcher files only new drift. It may not advance the baseline, approve an
exception, weaken a validator, or refactor code in its detection cycle.

## MemBerry boundary

| Available | Unavailable |
|---|---|
| Load symbols, dependencies, aspects, impact, drift, decisions, failures, PR impact, and provenance. | Discover from repository source, executable checks, runtime wiring, history, and committed state. |
| Store human-approved rules and decisions with manifest path and commit. | Keep the same information in policy, evidence, decisions, and verification ledger. |

Both paths run the same deterministic validators. Memory downtime may reduce
explanation quality; it may never change pass/fail.
